Part 1: Project Summary
Overview
The project is a multi-drone routing simulation system. A fleet of K drones must be routed from a unique start hub to a unique end hub across a weighted graph of zones, in the minimum number of simulation turns (makespan). The system must parse an input map file, compute optimal or near-optimal routes using CA*, simulate the movement turn by turn, and display the result visually.


Input Format
The system reads a map file with the following structure:

    nb_drones: <positive_integer>
    start_hub: <name> <x> <y> [metadata]
    end_hub:   <name> <x> <y> [metadata]
    hub:       <name> <x> <y> [metadata]
    connection: <zone1>-<zone2> [metadata]
    # comments are ignored

Zone metadata fields (all optional):

    zone=<type>         default: normal
    color=<value>       default: none
    max_drones=<int>    default: 1

Connection metadata fields (all optional):

    max_link_capacity=<int>    default: 1

Zone Types
Type, Movement Cost, Rule
normal, 1 turn, Standard movement
restricted, 2 turns, Drone must commit — cannot wait mid-transit
priority, 1 turn, Same cost as normal but preferred by pathfinding
blocked, —, Inaccessible — no drone may enter


Hard Constraints

Parser:
- First line must define nb_drones
- Exactly one start_hub and one end_hub
- Every zone name must be unique, no dashes or spaces in names
- No duplicate connections (a-b and b-a are the same)
- Zone types must be one of the four valid types
- Capacity values must be positive integers
- Any violation stops the program with a clear error message including line number and cause

Movement and occupancy:
- A zone may hold at most max_drones drones simultaneously (default 1)
- Start hub: unlimited capacity at turn 0
- End hub: unlimited capacity always
- A connection may be traversed by at most max_link_capacity drones per turn (default 1)
- Drones moving out of a zone free capacity for that same turn
- A drone entering a restricted zone must arrive on the next turn — it cannot wait on the connection
- Blocked zones cannot be entered under any circumstances

Simulation output:
- One line per turn listing all drone movements: D<ID>-<zone> or D<ID>-<connection> for restricted transit
- Drones that do not move are omitted
- Drones that reach End are no longer tracked
- Simulation ends when all drones reach End

Technical:
- No graph libraries (networkx, graphlib, etc.)
- Fully type-safe — mypy and flake8 must pass
- Fully object-oriented
- Visual feedback required (colored terminal output or graphical display)


Performance Benchmarks

Difficulty, Target
Easy maps, ≤ 10 turns
Medium maps, 10–30 turns
Hard maps, < 60 turns
Challenger (optional), ≤ 45 turns

Part 3: CA* Algorithm Description

Overview
Cooperative A* (CA*) is a multi-agent pathfinding algorithm that routes agents one at a time through a space-time graph, using a shared reservation table to prevent conflicts. It was introduced by David Silver in 2005 and is the practical standard for multi-agent routing problems where near-optimal makespan is required without the exponential cost of globally optimal algorithms like CBS.

The Space-Time Graph
Rather than searching a plain graph of zones, CA* searches a graph where every node is a (zone, turn) pair. This means the same physical zone appears as a different node at each turn — (A, 1), (A, 2), (A, 3) are all distinct nodes. This allows the algorithm to reason about when a drone is somewhere, not just where it is.
The graph is never fully constructed — nodes and edges are generated on demand during A*, keeping memory usage at O(K × T) rather than O(V × T).
From any node (zone, t), two types of moves are possible:
Wait:   (zone, t) → (zone, t+1)              cost = 1
Move:   (zone, t) → (neighbour, t+cost)      cost depends on zone type

The Reservation Table
The reservation table is a shared dictionary updated after each drone is routed. It records how many drones occupy each (zone, turn) cell and each (connection, turn) cell. During A*, any node that would exceed its capacity limit is treated as a wall — the drone cannot go there.
Three types of reservations are maintained:
Zone reservation:       (zone_name, turn)              → drone count
Connection reservation: (zone_a, zone_b, turn)         → drone count
Transit reservation:    (from_zone, to_zone, turn)     → drone count
Transit reservations handle the restricted zone commit rule — a drone entering transit toward a restricted zone reserves the mid-transit cell, preventing another drone from entering the same connection simultaneously, and the destination cell is checked at planning time to ensure it will be free on arrival.

Zone Type Handling
Zone type, Move cost, Special rule
normal, 1, Standard
priority, 0.9, Slightly preferred by A*
restricted, 2, Checks both transit and destination availability before committing
blocked, ,Never generated as a neighbour

The Heuristic
Before any drone is routed, Dijkstra is run once on the original graph in reverse from End, ignoring all capacities and other drones. This produces h(zone) — the true shortest path cost from any zone to End in an uncongested graph.
This heuristic is:

Admissible — never overestimates, since the real path can only be longer due to congestion
Consistent — satisfies h(X) ≤ cost(X→Y) + h(Y) for all edges
Topology-aware — reflects actual graph structure and zone types, not geometric distance


The Full Algorithm
1. Pre-compute h(zone) for all zones via reverse Dijkstra from End

2. Sort drones by h(start) ascending (shortest estimated path first)

3. For each drone in sorted order:
     a. Run A* on the space-time graph from (Start, start_turn) to End
     b. At each node (zone, t), generate neighbours:
          - Wait: (zone, t+1) if zone not at capacity at t+1
          - Normal/priority move: (neighbour, t+1) if zone and connection not at capacity
          - Restricted move: (neighbour, t+2) if transit and destination both free
          - Blocked: skip
     c. For each neighbour, check reservation table — skip if at capacity
     d. Use f = g + h to prioritise frontier
     e. When End is reached, reconstruct path via came_from links
     f. Register all (zone, turn) and (connection, turn) cells in reservation table

4. Repeat steps 2–3 with longest-first ordering
   Keep whichever ordering produces the smaller makespan

5. Pass all drone paths to the Simulator for turn-by-turn execution

Complexity, Value
Pre-computation (reverse Dijkstra), O((V+E) log V) — oncePer-drone 
A*, O(V × T × log(V × T))
Full routing (K drones), O(K × V × T × log(V × T))
Memory (reservation table), O(K × T)
Memory (space-time graph) O(V × T) lazily — only visited nodes
Where V = zones, E = connections, K = drones, T = turn horizon.

Why CA* for This Project

Routes drones sequentially with full conflict prevention — no post-hoc collision fixing needed
All project constraints (zone capacity, link capacity, restricted commit rule, blocked zones, priority zones) map cleanly onto the reservation table and A* expansion logic
Memory-efficient — no full graph materialisation
Near-optimal makespan in practice — the two-ordering retry strategy closes most of the gap with globally optimal algorithms
Implementable without any graph libraries — only a priority queue (Python's built-in heapq) and standard data structures are needed
Naturally type-safe and object-oriented — every component maps to a clean class
